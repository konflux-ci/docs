= Debugging Integration Tests
:description: Finding failed integration PipelineRuns via activity views and logs.

In case of an integration test scenario failing, there are several steps to take in order to debug the issue before rerunning the test in question. These steps are outlined below.


.Prerequisites
- You have a snapshot that has completed all build-time tests. These must be completed before attempting to debug the failed test.

- You have access to the {ProductName} UI in order to view the logs of the failed test.

.Procedure

. Identify the IntegrationTestScenario that has failed
    * Open the {ProductName} and navigate to Application/your_application_name/activity
    * Select "Pipeline Runs" under "Activity By"
    * Your view should look similar to the below image.

+
image::activityview.png[role="border" alt="Activity View"]

. Click on the pipeline run that has a status of "Failed". This will take you to a detailed view of the failed run.

. Examine the "Log Snippet" section on the right side of this page. It contains the most recent error returned by the integration test. For more comprehensive logs, click on "See Logs". See the below image for reference.

+
image::testfailed.png[role="border" alt="Test Failed"]

. In this example the output suggests that the pipelineRun is missing an expected parameter, "username". To edit the integration test, follow the procedure provided xref:testing:integration/editing.adoc[here].

. Rerun the test by following the steps xref:testing:integration/rerunning.adoc[here].

. Once the test has been rerun, verify that the test has passed by checking the "Pipeline Runs" tab in the {ProductName} console. The status of the test should now be "Succeeded". See the below image for reference.

+
image::successfulretest.png[role="border alt="Successful Retest"]

[#resolution-took-longer-than-global-timeout]
== Test fails with "resolution took longer than global timeout"

The integration PipelineRun fails before any task starts, so it has no task logs. Its status has the reason `CouldntGetPipeline` and an error such as the following:

----
resolver failed to get Pipeline : error requesting remote resource:
resolution took longer than global timeout of 1m0s
----

To see the full status, run `kubectl get pipelinerun <pipelinerun-name> -o yaml` and read `status.conditions`. The duration in the message is the resolution limit of your cluster. The git resolver did not fetch your pipeline definition within this limit. This usually happens in clone mode, when the pipeline is in a large repository or the Git server responds slowly.

To fix it:

. Rerun the test. If the Git server is slow only for a short time, the rerun succeeds. See xref:testing:integration/rerunning.adoc[Rerunning an integration test].
. If the error persists, switch the test to SCM API mode, or move the pipeline to a small repository that holds only Tekton definitions. To switch to SCM API mode:
.. Create an access token and store it in a secret in your namespace. See xref:building:secrets/creating-scm-secrets.adoc[Creating source control management secrets].
.. In `spec.resolverRef.params`, replace the `url` parameter with the SCM API parameters. See xref:testing:integration/creating.adoc#switching-to-scm-api-mode[Switching an existing test to SCM API mode].
.. Rerun the test.

== Checking the service account of a test

An integration PipelineRun for a component snapshot normally uses the `its-pipeline-<component-name>` service account. To see which service account a PipelineRun used, run `kubectl get pipelinerun <pipelinerun-name> -o yaml` and read `spec.taskRunTemplate.serviceAccountName`. The annotations are under `metadata.annotations`.

If the PipelineRun used `konflux-integration-runner` and has the `test.appstudio.openshift.io/service-account-fallback` or `integration.konflux-ci.dev/service-account-fallback` annotation, the value of the annotation is the reason. For the values, see xref:testing:integration/creating.adoc#service-account-of-the-integration-pipelinerun[Service account of the integration PipelineRun].

The annotation is set only when {ProductName} replaced `its-pipeline-<component-name>` with `konflux-integration-runner`. It does not explain other failures.

If the PipelineRun used `its-pipeline-<component-name>` and the test failed with a `forbidden` error, a Role that you bound to `konflux-integration-runner` might not be bound to the service account of the component. See xref:testing:integration/creating.adoc#roles-bound-to-konflux-integration-runner[Roles that you bound to konflux-integration-runner].
